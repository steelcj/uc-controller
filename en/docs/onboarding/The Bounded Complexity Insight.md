# Controller node ingress - The Bounded Complexity Insight

## The Bounded Complexity Insight

The most important thing to understand about multi-source ingress is that:

*  source diversity is bounded to the raw  to onboard transition

Once a node completes onboarding, it is on SSH as a known user with passwordless sudo. Normalize and specialize never need to know whether the node started as an Incus container, a cloud VM, or a bare-metal box. The onboard stage is the great equalizer.

This means the complexity is contained. You don't need conditional connection logic in `20_normalize.yml` or `30_specialize.yml`. The multi-source problem lives entirely in discovery and onboarding.

## The Core Problem: The SSH Assumption

The v0.1.3 `10_onboard.yml` has two plays and assumes SSH from the start:

```yaml
- name: wait for SSH
 wait_for:
 host: "{{ ansible_host | default(inventory_hostname) }}"
 port: 22
 timeout: 30
 delegate_to: localhost
```

This works for cloud VMs, nmap-discovered nodes, and pre-provisioned bare metal. It fails immediately for Incus containers, which have no SSH listener until the onboard play installs one.

Your onboarding document already solves this for Incus with a five-play structure: validate → bootstrap Python → converge baseline → switch to SSH → verify. The challenge is generalizing that structure so a single `10_onboard.yml` handles both paths without duplicating the playbook per source.

### Inventory Architecture for Multi-Source

The raw inventory needs to support two fundamentally different discovery mechanisms:

**Plugin-based sources** (Incus, LXD, Docker, cloud providers) use Ansible inventory plugins that auto-discover at runtime. No file is written. The plugin config lives in the raw inventory directory:

```text
inventories/raw/
├── incus.yml # community.general.incus plugin config
├── aws.yml # amazon.aws.aws_ec2 plugin config (if added later)
├── hosts.yml # generated by 00_discover.yml (nmap, API)
├── group_vars/
│ ├── all.yml # shared raw vars (ansible_python_interpreter, etc.)
│ ├── incus.yml # ansible_connection: community.general.incus
│ └── raw_ssh.yml # ansible_connection: ssh (default)
└── host_vars/
```

**Generated sources** (nmap, custom API, CMDB) produce a static `hosts.yml` written by `00_discover.yml`. The hosts land in a `raw` group (or source-specific subgroups).

The key is that **source-specific connection variables live in `group_vars` keyed to the source's group.** The Incus plugin creates groups like `incus`, `incus_local`, `incus_local_default`. A `group_vars/incus.yml` in the raw inventory sets:

```yaml
# inventories/raw/group_vars/incus.yml
ansible_connection: community.general.incus
ansible_user: root
ansible_become: no
```

For nmap-discovered hosts, the generated `hosts.yml` places them in a `raw` group, and `group_vars/raw.yml` sets:

```yaml
# inventories/raw/group_vars/raw.yml
ansible_connection: ssh
ansible_user: root
ansible_become: yes
```

The playbook doesn't need to know the source. It reads `ansible_connection` from the inventory and adapts.

### Discovery: Plugin vs. Generated

The current `00_discover.yml` handles nmap and cloud API, both of which write a static `hosts.yml`. Plugin-based sources don't need it at all — the Incus plugin discovers containers at runtime.

This means discovery splits into two categories:

| Discovery type | Mechanism | When it runs | Needs `00_discover.yml`? |
|---|---|---|---|
| Plugin-based | Ansible inventory plugin | At playbook start (every run) | No |
| Generated | Playbook writes `hosts.yml` | On demand (operator runs `00_discover.yml`) | Yes |
| Manual | Operator edits `hosts.yml` | On demand | No |

For plugin-based sources, `00_discover.yml` is a no-op — the plugin handles it. For generated sources, `00_discover.yml` writes the file and calls `meta: refresh_inventory`. For manual entry, neither is needed.

The practical implication: when running `10_onboard.yml` for Incus, you pass `-i inventories/raw/incus.yml` and the plugin discovers at runtime. When running for nmap-discovered nodes, you pass `-i inventories/raw/hosts.yml` (or the directory). The `-i` flag selects the source.

### The Connection Transition Pattern

The generalized `10_onboard.yml` has five plays. SSH-ready sources skip the bootstrap and transition plays via `when` conditions. Non-SSH sources run all five.

**Play 1: Validate and promote (all sources)**

```yaml
- name: validate and promote raw nodes
 hosts: raw
 gather_facts: no
 tasks:
 - name: wait for SSH (SSH-ready sources)
 wait_for:
 host: "{{ ansible_host | default(inventory_hostname) }}"
 port: 22
 timeout: 30
 delegate_to: localhost
 when: ansible_connection | default('ssh') in ['ssh', 'paramiko_ssh', 'smart']

 - name: confirm reachability (Incus sources)
 command: "incus exec {{ inventory_hostname }} -- true"
 delegate_to: localhost
 when: ansible_connection | default('ssh') == 'community.general.incus'
 changed_when: false

 - name: promote to onboarded group
 add_host:
 name: "{{ item }}"
 ansible_host: "{{ hostvars[item].ansible_host | default(item) }}"
 groups:
 - onboarded
 - "{{ target_group | default('ungrouped') }}"
 loop: "{{ ansible_play_hosts }}"
```

The `when` condition on the reachability check is what makes this work for mixed sources. You could also add checks for Docker (`docker exec`), libvirt, etc.

**Play 2: Bootstrap Python (non-SSH sources only)**

```yaml
- name: bootstrap Python on non-SSH sources
 hosts: onboarded
 gather_facts: no
 tasks:
 - name: install Python
 raw: "apt-get update && apt-get install -y python3"
 when: ansible_connection | default('ssh') not in ['ssh', 'paramiko_ssh', 'smart']
 # This play uses whatever connection the source sets (Incus, Docker, etc.)
```

SSH-ready sources skip this play entirely. Non-SSH sources install Python over their native connection. The `raw` module works because it doesn't require Python on the target.

**Play 3: Converge baseline (all sources)**

```yaml
- name: converge onboard baseline
 hosts: onboarded
 become: "{{ ansible_become | default('yes') }}"
 gather_facts: yes
 vars:
 firewall_rules: >-
 {{
 (firewall_rules_onboard | default([]))
 }}
 roles:
 - role: robertdebock.bootstrap
 - role: robertdebock.epel
 - role: robertdebock.update
 - role: robertdebock.locale
 - role: robertdebock.auto_update
 - role: robertdebock.cron
 - role: robertdebock.ntp
 - role: robertdebock.openssh
 - role: robertdebock.fail2ban
 - role: robertdebock.firewall
 - role: robertdebock.users
```

The role list is identical for all sources. `ansible_connection` is still whatever the source set (Incus, SSH, etc.), so roles run over the source's native connection. `become` is sourced from the inventory — Incus sets `ansible_become: no` (already root), SSH sets `ansible_become: yes`.

**Play 4: Transition to SSH (non-SSH sources only)**

```yaml
- name: transition to SSH connection
 hosts: onboarded
 gather_facts: no
 tasks:
 - name: switch connection to SSH as initial user
 set_fact:
 ansible_connection: ssh
 ansible_user: "{{ initial_user | default('initial') }}"
 ansible_ssh_private_key_file: "{{ initial_ssh_key_file }}"
 ansible_become: yes
 when: ansible_connection | default('ssh') not in ['ssh', 'paramiko_ssh', 'smart']

 - name: reset connection to apply new settings
 meta: reset_connection
 when: ansible_connection | default('ssh') not in ['ssh', 'paramiko_ssh', 'smart']
```

Wait — there's a subtlety here. After `set_fact` changes `ansible_connection`, the `when` condition on the next task would re-evaluate against the *new* value. So the `meta: reset_connection` task needs to run unconditionally, or the condition needs to capture the original value before the switch.

The safer pattern is to capture the source connection at the top of the play:

```yaml
- name: transition to SSH connection
 hosts: onboarded
 gather_facts: no
 vars:
 source_connection: "{{ ansible_connection | default('ssh') }}"
 tasks:
 - name: switch connection to SSH as initial user
 set_fact:
 ansible_connection: ssh
 ansible_user: "{{ initial_user | default('initial') }}"
 ansible_ssh_private_key_file: "{{ initial_ssh_key_file }}"
 ansible_become: yes
 when: source_connection not in ['ssh', 'paramiko_ssh', 'smart']

 - name: reset connection to apply new settings
 meta: reset_connection
 when: source_connection not in ['ssh', 'paramiko_ssh', 'smart']
```

`vars:` is evaluated once at play start, so `source_connection` captures the original value before any `set_fact` changes it. The `when` conditions reference `source_connection`, not the live `ansible_connection`, so they don't flip mid-play.

**Play 5: Verify SSH (all sources)**

```yaml
- name: verify SSH and sudo
 hosts: onboarded
 gather_facts: no
 tasks:
 - name: confirm SSH login
 ping:

 - name: confirm passwordless sudo
 command: sudo -n true
 changed_when: false
```

By this point, all sources are on SSH. The verify play is source-agnostic.

### Source-Specific Variables

Each source needs its own connection variables. These live in the raw inventory's `group_vars`, keyed to the groups the source's inventory plugin creates.

| Source | Group | `ansible_connection` | `ansible_user` | `ansible_become` |
|---|---|---|---|---|
| Incus | `incus` | `community.general.incus` | `root` | `no` |
| LXD | `lxd` | `community.general.lxd` | `root` | `no` |
| Docker | `docker` | `community.general.docker` | `root` | `no` |
| SSH-ready | `raw` | `ssh` (default) | `root` | `yes` |
| Cloud (AWS) | `aws_ec2` | `ssh` | `ec2-user` or `root` | `yes` |

The `ansible_become` distinction matters: Incus/Docker connections already run as root, so `become: yes` with `become_method: sudo` would try to invoke `sudo` which may not exist in a minimal container. Setting `ansible_become: no` for container sources avoids that.

### Naming and Limiting

Each source has its own host naming convention:

- **Incus**: `instance.project.remote` (e.g., `ex2-test.default.local`)
- **nmap**: IP-derived (e.g., `192-168-1-10`)
- **Cloud**: instance name or tag-based
- **Manual**: operator-chosen

The `--limit` flag must match the source's naming. Your onboarding document handles this with `'ex2-test*'` globs. For multi-source runs, you'd limit by source group: `--limit incus` or `--limit raw`.

### What v0.1.3 Needs to Change

1. **`10_onboard.yml`**: Expand from 2 plays to 5. Add conditional reachability checks, Python bootstrap, connection transition, and SSH verification. The role list stays the same.

2. **Raw inventory structure**: Add source-specific `group_vars` files (`incus.yml`, `raw.yml`) that set `ansible_connection`, `ansible_user`, `ansible_become`. Add plugin config files (`incus.yml`) alongside the generated `hosts.yml`.

3. **`00_discover.yml`**: No structural change, but document that it's only for generated sources. Plugin-based sources skip it.

4. **Usage examples**: Show both paths — plugin-based (Incus) and generated (nmap) — with the appropriate `-i` flags.

5. **`ansible.cfg`**: The default `inventory` setting should point to the raw directory (not a specific file), so multiple sources can coexist. Or remove the default and always pass `-i` explicitly.

### Open Questions

**Mixed-source runs.** Can you onboard Incus containers and SSH-ready nodes in the same `10_onboard.yml` run? Technically yes — the `when` conditions handle it. But the `-i` flags need to include both inventory sources, and the host naming conventions differ. It may be cleaner to run per-source and let `site.yml` chain them sequentially with different inventories. Is that a use case you need, or is per-source onboarding acceptable?

**`become` on container connections.** Does `community.general.incus` handle `become: yes` gracefully (no-op since already root), or does it try to invoke `sudo`? Your onboarding document doesn't mention this as a problem, which suggests it either works or you've set `ansible_become: no` in the Incus group_vars. Worth confirming.

**The `initial` user creation.** Play 4 assumes `robertdebock.users` (run in play 3) created the `initial` user with the right SSH key and sudo. If the users role doesn't run for some reason, the SSH transition fails. Should play 4 verify the user exists before switching, or is the role dependency sufficient?

**Firewall during transition.** The firewall role runs in play 3 (over the source connection). If the source is Incus, the firewall opens port 22 over the Incus connection. Then play 4 switches to SSH. The firewall is already correct. But if the firewall role fails, SSH won't be reachable and play 4 fails. Should there be a fallback to the source connection if the SSH transition fails?
